# AutoRepairOS UX 順手度檢視

> 方法：本機跑起來（port 8092，用 `data/autorepair.db` 的複本），
> 以 owner 登入後逐頁抓 HTML，量測**實際操作面**（步驟數、選項數、欄位數）。
> 沒有改任何程式。量測當下的數字如下。

## 一、先看每天在用的三個流程（依 CAR35 頻率：維修單 / 收款 / 進貨）

| 流程 | 現況 | 實測問題 |
|---|---|---|
| 開工單 | 導覽「工單」→「＋開立新工單」→ 車輛即時搜尋 → 填 15 欄 → 建立 | 技師下拉 61 個選項，含**行政人員與眷屬** |
| 查工單 | 導覽「工單」→ 關鍵字／狀態／日期 → 搜尋 | **分頁其實有**（每頁 50，共 1,717 頁），缺的是技師篩選 |
| 結帳 | 工單詳情 →「🧾 收據列印」→「標記為已結帳」 | 狀態／核准／SOP 是三個獨立表單 |

### 開工單：車輛欄位其實設計得不錯

`vehicle_id_fallback`（501 個選項）包在 `<noscript>` 裡，正常情況用的是
即時搜尋框（placeholder「輸入車牌 / 車型 / 車主 / 電話」），資料走 JSON
前端篩選。**這一項不用改。** 要確認的只有 JS 失效時退回 501 項原生下拉仍可操作。

### 技師下拉：把行政與眷屬都列進來了（實測清單）

```
未指派, 技師 (tech), 江銘鴻 (D003),
何財王常 (G18)　引擎, 劉仁傑 (G033)　引擎, 古存宏 (G035)　引擎, …
… 陳淑娟 (G005)　行政, 陳素珠 (E004)　行政, 黃玟捷 (E006)　行政
```

`technicianOptions()`（`internal/handler/workorders.go:768`）原本只過濾
`role='technician' AND staff_kind='employee'`，**沒有過濾 `staff_branch`**。
資料實況：

| 條件 | 人數 |
|---|---:|
| `role='technician' AND staff_kind='employee'` | 61 |
| 其中 `staff_branch='E'`（行政） | **9**（`E001`–`E006`、`E02-4`、`G005`、`G14`） |
| 修正後下拉選項 | **52**（61 − 9，含「未指派」與「技師 (tech)」） |

→ 這 9 人是行政人員，選錯不會報錯，但會污染技師產值與佣金統計。

**查證過程中一度誤判**：以為 40 個 `G` 開頭的帳號是眷屬。實際上
`staff_kind='dependent'` 的 40 人（`A07-1`、`B01-1`、`E02-1`…，全部
`staff_branch='G'`）**早已被正確排除**；`G001`、`G011` 這些 `G` 開頭帳號
是 `staff_kind='employee'` 的正常員工編號（部門是 A/B/C/D）。
教訓：判斷前先查 `staff_kind` 的分布，不要從帳號前綴推論。

### 工單列表：分頁沒問題，缺的是篩選維度

`工單列表（符合條件 85825 筆）`，分頁每頁 50、共 1,717 頁（`?page=1717`），
有 perPage 選擇器。篩選只有 `q`（車牌/車主/電話）、`status`、`from`、`to`。
**缺技師篩選**（`technician_id` 不在查詢參數裡）。
另一個實測問題：第一頁被 7 筆 `TEST-8888` 測試資料佔滿。

## 二、首頁

六個數字卡：`75 待處理工單`、`57 進行中`、`7530 待結帳`、
`6512 客戶數`、`12964 車輛數`、`8669 低庫存件`。

- **卡片不可點**（純文字，沒有 `<a>`）。看到「7530 待結帳」想處理，
  得自己去導覽找「工單」再自己下篩選條件。
- 「最近工單」顯示 `TEST-8888 / Toyota Altis / 測試客戶`
  —— 測試資料排在最前面，正式資料在下面（最新真實工單是 2023/12）。
- 有 `8669 低庫存件` 這個警訊數字，但沒有對應的處理入口。

## 三、導覽結構

單層 15 個連結：
`總覽 客戶 車輛 工單 保險公司 庫存 廠商 員工 投保 定檢 保養套餐 技師佣金 支出 報表 排程`

- **沒有分組**：每天用的（工單／客戶／車輛）跟三個月用一次的
  （保養套餐／技師佣金／排程）並排，視覺權重相同。
- **同義詞混用**：「工單」與「技師佣金」；「客戶」與「廠商」與「員工」；
  「投保」與「保險公司」—— 後兩者對使用者來說極易混淆
  （「保險公司」是主檔，「投保」是紀錄）。
- **「支出」對應的 CAR35 功能已停用 10 年**（見 `CAR35_USAGE_FREQUENCY.md`），
  卻仍在主導覽第一層。

## 四、工單詳情頁

實測 **654 KB** HTML（單張工單），四個獨立表單：

```
/work-orders/1153153/status      ← 按鈕「更新」
/work-orders/1153153/approval    ← 按鈕「更新」
/work-orders/1153153/sop         ← 按鈕「標記 SOP 完成」
/work-orders/1153153/items       ← 按鈕「加入項目」
```

**兩個按鈕同名「更新」**，使用者無法從文字知道哪個更新什麼。

## 五、對照 Nielsen 十大原則（只列有實證的）

| 原則 | 現況 | 證據 |
|---|---|---|
| 系統狀態可見性 | 收據頁有「LINE 估價單：客戶未綁定 line_user_id」但**沒有綁定入口** | 使用者看到問題卻無法行動 |
| 系統與真實世界一致 | 技師清單含行政人員 | 60 人下拉，9 人 `staff_branch='E'` |
| 使用者控制與自由 | 工單狀態只能整批送出，不能只改一項 | 三個獨立表單 |
| 一致性與標準 | 工單詳情兩個按鈕都叫「更新」 | `Counter({'更新': 2, ...})` |
| 錯誤預防 | 技師下拉未過濾部門 | `technicianOptions()` 查詢條件 |
| 辨識而非回憶 | 首頁數字不可點，要記住路徑 | 6 張卡片皆無連結 |
| 效率與彈性 | 工單列表無技師篩選；無「我的待辦」 | 查詢參數只有 q/status/from/to |
| 美觀與極簡 | 15 個同權重導覽項 | 導覽列 |
| 錯誤恢復 | 無批次操作，逐筆刪除 | `items/{id}/delete` 連結 |

## 七、量測腳本

上述數字都能重跑：

```bash
cd C:/Users/fr/AutoRepairOS
export PATH="$PATH:/c/Program Files/Go/bin"
go build -o "$TMPDIR/ar_ux.exe" .
cp data/autorepair.db "$TMPDIR/ux_copy.db"
PORT=8092 DB_PATH="file:$TMPDIR/ux_copy.db?_busy_timeout=5000" "$TMPDIR/ar_ux.exe" &
python scripts/ux_probe.py --base http://localhost:8092 --out "$TMPDIR/ux_snap"
```

> **務必用複本 DB**。直接對 `data/autorepair.db` 啟動，排程器會立刻寫入
> 每日備份與通知（實測啟動 1 秒內就產生 `data/backups/*.db`）。
