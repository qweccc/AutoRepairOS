## Architecture / proposed approach

**身分（#3）**：把 `components.Layout` 的第二、三個參數從 `(username, role string)` 改成 `(user model.User)`。這樣「傳錯身分」在**編譯期**就不可能發生——`"owner"` 不是 `model.User`，編譯器會直接擋下來。這比加測試更強：不是檢查錯誤，是讓錯誤寫不出來。

**角色（#4）**：`internal/nav` 的 `Route` 加 `Roles []string`（空＝所有人可見），`Render(active, role)` 依角色過濾；頁面上的操作按鈕改為由 handler 傳入 `model.User` 後條件渲染。導覽與按鈕共用同一份角色定義，不再各寫一次。

**授權（#1）**：在工單詳情頁加一個「追加維修」區塊（櫃檯填項目 → 建立授權 + 推 LINE 連結），並補完 `approvals.go:306` 的 TODO：客戶同意時在**同一個交易**內把項目寫進 `work_order_items`。

```go
	"path/filepath"
	"regexp"
	"strings"

// 這些頁面的 Layout 呼叫把登入者/角色寫死，會讓頁首顯示錯誤的帳號。
// 用原始碼掃描而不是 HTTP 測試：這類錯誤是「某個頁面忘了傳」，掃描才能
// 覆蓋全部頁面（HTTP 測試要對 28 個頁面各登入一次，慢且容易漏）。
func TestNoTemplPageHardcodesLayoutIdentity(t *testing.T) {
	files, err := filepath.Glob(filepath.Join("..", "..", "web", "pages", "*.templ"))
	if err != nil || len(files) == 0 {
		t.Fatalf("找不到 web/pages/*.templ：%v（共 %d 檔）", err, len(files))
	}

	// 抓 Layout( 後面緊接的兩個字串字面值參數
	re := regexp.MustCompile(`components\.Layout\(\s*[^,]+,\s*[^,]+,\s*("[^"]*")\s*,\s*("[^"]*")`)
	bad := []string{}
	for _, f := range files {
		body, err := os.ReadFile(f)
		if err != nil {
			t.Fatal(err)
		}
		for _, m := range re.FindAllStringSubmatch(string(body), -1) {
			bad = append(bad, filepath.Base(f)+": 寫死 "+m[1]+", "+m[2])
		}
	}
	if len(bad) > 0 {
		t.Errorf("Layout 的登入者/角色不可寫死，應傳 model.User（共 %d 處）：\n  %s",
			len(bad), strings.Join(bad, "\n  "))
	}
}
```

#### T1.2 批次改 28 個呼叫點（用腳本，不要手改）

#### T4.2 定義追加項目的傳輸格式

`item_summary` 目前是自由文字。為了讓 TODO 能安全地寫入 `work_order_items`，改成 JSON。新增型別於 `internal/handler/approvals.go`：

```go
// approvalItem 是追加維修項目在 approval_requests.item_summary 裡的元素。
//
// 為什麼要結構化：原設計把 item_summary 當自由文字，導致客戶同意後
// 無法可靠地還原成工單項目（approvals.go 的 TODO 就是卡在這裡）。
// 存 JSON 讓「客戶同意什麼」與「工單加了什麼」是同一份資料。
type approvalItem struct {
	Description string  `json:"description"`
	Quantity    int     `json:"quantity"`
	UnitPrice   float64 `json:"unit_price"`
	ItemType    string  `json:"item_type"` // labor / part / subcontract
}

func parseApprovalItems(raw string) ([]approvalItem, error) {
	var items []approvalItem
	if err := json.Unmarshal([]byte(raw), &items); err != nil {
		return nil, fmt.Errorf("追加項目格式錯誤: %w", err)
	}
	if len(items) == 0 {
		return nil, errors.New("追加項目不可為空")
	}
	for i, it := range items {
		if strings.TrimSpace(it.Description) == "" {
			return nil, fmt.Errorf("第 %d 項缺少品名", i+1)
		}
		if it.Quantity <= 0 {
			return nil, fmt.Errorf("第 %d 項數量必須大於 0", i+1)
		}
		if it.UnitPrice < 0 {
			return nil, fmt.Errorf("第 %d 項單價不可為負", i+1)
		}
		switch it.ItemType {
		case "labor", "part", "subcontract":
		default:
			return nil, fmt.Errorf("第 %d 項類別無效: %q", i+1, it.ItemType)
		}
	}
	return items, nil
}
```

（需要 import `encoding/json`、`errors`、`fmt`、`strings`。）

```go
// CreateApprovalFromWorkOrder 由櫃檯在工單詳情頁建立追加維修授權。
//
// 為什麼需要這支：CreateApprovalRequest 原本沒有任何人呼叫（只出現在註解），
// 所以「產生連結 → 客戶確認 → 工單加入追加項目」這條流程從 UI 根本走不完。
func CreateApprovalFromWorkOrder(w http.ResponseWriter, r *http.Request) {
	woID := mustInt(r.PathValue("id"))
	woPath := "/work-orders/" + strconv.FormatInt(woID, 10)

	var customerID int64
	var status string
	if err := db.DB.QueryRow(`SELECT customer_id, status FROM active_work_orders WHERE id = ?`, woID).
		Scan(&customerID, &status); err != nil {
		http.NotFound(w, r)
		return
	}
	// 已結帳的工單是財務憑證，不能再追加項目（與 requireOrderMutable 一致）
	if status == "paid" {
		redirectErrMsg(w, r, woPath, "此工單已結帳，不可再追加項目。如需更正請另行開立沖銷單")
		return
	}

	items := []approvalItem{{
		Description: strings.TrimSpace(r.FormValue("description")),
		Quantity:    atoiDefault(r.FormValue("quantity"), 0),
		UnitPrice:   atofDefault(r.FormValue("unit_price"), 0),
		ItemType:    strings.TrimSpace(r.FormValue("item_type")),
	}}
	// 用同一支驗證函式，避免 UI 與解析端對規則的認知不一致
	raw, err := json.Marshal(items)
	if err != nil {
		fail(w, "建立授權失敗")
		return
	}
	if _, err := parseApprovalItems(string(raw)); err != nil {
		redirectErrMsg(w, r, woPath, err.Error())
		return
	}

	req, err := CreateApprovalRequest(woID, customerID, string(raw))
	if err != nil {
		log.Printf("建立追加維修授權失敗（工單 #%d）: %v", woID, err)
		redirectErrMsg(w, r, woPath, "建立授權失敗："+err.Error())
		return
	}
	redirectMsg(w, r, woPath, "已建立追加維修授權，並已推播給客戶（連結 24 小時內有效）")
	_ = req
}
```

```go
func CheckApprovalForStatus(woID int64, targetStatus string) error {
	if targetStatus != "completed" && targetStatus != "paid" {
		return nil
	}
	var pending int
	if err := db.DB.QueryRow(`SELECT COUNT(1) FROM approval_requests
		WHERE work_order_id = ? AND status = 'pending' AND expires_at > datetime('now','localtime')`,
```

```js
      // 草稿只在送出成功後才清除。
      // 原本在 submit 事件就 remove：離線或伺服器錯誤時草稿會被丟掉，
      // 使用者重整後什麼都沒了——而草稿存在的意義正是「送不出去時別弄丟」。
      form.addEventListener('htmx:afterRequest', function (evt) {
        if (evt.detail && evt.detail.successful) {
          Drafts.remove(key).catch(function () {});
        }
      });
      form.addEventListener('submit', function (evt) {
        // 非 HTMX 的一般表單送出無法得知結果，保守起見保留草稿；
        // 由下一次成功送出或使用者手動清除來收尾。
        if (evt.defaultPrevented) return;
      });
```

## Risks, tradeoffs, and open questions

### 風險

| 風險 | 影響 | 對策 |
|---|---|---|
| Phase 1 動 28 個 templ 檔 + 產生碼 | 大範圍 diff，容易與其他 agent 的改動衝突 | 先確認工作樹乾淨、建立分支；`templ generate` **不可與其他 agent 並行跑**（會產出損毀的 `*_templ.go`） |
| Phase 2 的 `Roles` 抄錯 | 技師看不到該看的頁面（比看得到進不去更糟） | `Roles` 逐條 `grep main.go` 核對；完成後用三種角色各跑一次 nav 比對 |
| Phase 4 的 INSERT 欄位名照抄計畫 | 執行期 SQL 錯誤，功能全壞 | **先 `PRAGMA table_info(work_order_items)` 確認欄位名**，計畫中的 `unit_price` 是推定值 |
| SW `CACHE` 版本沒遞增 | 修好的 offline.js 在既有瀏覽器不生效 | T3.1 明列此步；驗證時用無痕視窗 |
| D2 若做錯（擋所有 pending） | **每張工單都無法完工** | 判準是「有未決 `approval_requests`」，不是工單上的 `approval_status`；測試要涵蓋「沒有授權的工單可以完工」 |

### 取捨

- **Phase 1 選 `model.User` 而非 context**：context 版需要新增全域認證中介層（目前 `main.go` 只有 `CSRFProtection`），會動到認證流程且風險高。`model.User` 一樣能讓編譯器擋住錯誤，blast radius 小得多。若日後要減少每請求的 DB 查詢，再另案做中介層。
- **Phase 4 先做「一次一項」**：`CreateApprovalRequest` 目前吃單一字串，一次多項需要改資料形狀與 UI（動態列）。追加維修在實務上通常一次一兩項，先做單項能最快讓流程可用。
- **D3 縮小承諾而非全面離線**：全面離線送出要處理 ID 衝突與庫存順序，成本高、車廠實際需求低。

### 需要你決定的事（動工前回覆即可）

1. **D1 預約→工單**：要不要做關聯（含 migration 045）？建議做。
2. **D2 未核准是否擋完工**：建議只擋「有未決授權」的工單。
3. **D3 離線範圍**：建議限縮成照片 + 修掉草稿被誤刪。
4. **D4 重複車牌**：建議加確認對話框。
5. **D5 技師導覽**：建議只顯示可用功能（Phase 2 已含）。
6. **D6 LINE/Telegram 欄位**：建議 LINE 移除、Telegram 保留（Phase 5 已含）。
7. **要不要出 release**：本計畫改動幅度大，建議全部完成、端到端驗收過後再 `bash build.sh`。

### 建議的執行順序與分批

```
Phase 0（安全網）
  ↓
Phase 1（身分）→ Phase 5（LINE 欄位）      ← 兩個都小、可先收斂
  ↓
Phase 2（角色）
  ↓
Phase 3（離線）
  ↓
Phase 4（授權，最大）
  ↓

  ↓

```
