## 0-1. 功能完整度快評

以「單店日常營運」來看，模組廣度已經很完整：工單、估價草稿、客戶/車輛、預約、定檢、保險與理賠、庫存/盤點、進貨與應付、收款與應收、照片與標記、SOP、技師工時/佣金、LINE/Telegram 通知、報表/分析、排程、備份（含照片）都有對應的頁面與資料表。

我沒有看到、或需要你確認是否在範圍內的是：

- **統一發票/字軌**：目前只有收據與稅額欄位，沒有發票號碼、字軌或電子發票介接。

## 1. P0 — 上線前必修（金流 / 帳號安全）

### P0-1. 預收或部分收款會直接把工單結帳（提前扣庫存、提前認列營收）

**位置**

- `internal/service/checkout.go:138-149`：新增收款後，只要 `receiptCompletesWorkOrder` 成立就呼叫 `checkoutTx`。
- `internal/service/checkout.go:322-335`：判斷條件只有「累計 `pay_total` >= 工單 `total_amount`」，**沒有檢查工單狀態**。
- `internal/handler/receivables.go:419-426`、`web/pages/stage7_forms.templ:349`：關聯工單是**自由輸入的工單編號**，沒有受限於「已完成」工單。
- 對照 `docs/USER_GUIDE_zh-TW.md:232`：「收款頁只會列出『已完成』的工單；若工單還在『進行中』，先在工單頁把它設成『已完成』，才能對它收款。」

**已重現**（暫時測試）

1. 建一張 `pending` 工單，總額 1,000，零件 2 個（庫存 8、預留 2）。
2. 新增一張 `pay_total=1000` 的收款並關聯該工單。
3. 結果：工單變成 `paid`、庫存扣到 6、預留變 2、客戶 `total_spent` 增加。
4. 但此時車還沒修，SOP/完工流程都被跳過。

**影響**

- 只是先收訂金／先付清，就會被當成「已完工已結帳」。
- 庫存提前扣、營收提前認列；之後要改單會被「已結帳不可變更」擋住，只能走目前不存在的沖銷流程。
- 手冊承諾的行為與程式不一致，櫃檯照手冊操作也會踩到。

**建議**

- `receiptCompletesWorkOrder` 加上 `wo.status = 'completed'`（本系統的「待結帳」）與 `total_amount > 0` 條件。
- 收款頁的「關聯工單」改成只允許選已完成工單（或輸入後驗證狀態），並在 service 層再擋一次。
- 若要支援訂金，應區分「預收款」與「結帳款」，不要用同一張 receivables 觸發結帳。

### P0-2. 0 元工單會被任何一筆收款自動結帳

**位置**：`internal/service/checkout.go:322-335`（沒有 `total > 0` 守門）、`internal/handler/receivables.go:405-411`（只擋四種付款與 `pay_total` 全為 0）。

**已重現**：`in_progress`、`total_amount=0` 的工單，新增 `pay_total=0` 的收款（service 呼叫）→ 工單變 `paid`、庫存扣減。

即使走 UI，`total=0` + 現金 50 也會成立（`50 >= 0`）。

**建議**：`total <= 0` 時不可自動結帳；另外 `checkoutTx` 也應拒絕 0 元工單（或要求明確的「零元結案」操作）。

### P0-3. 作廢收款不會沖回結帳、庫存與客戶累計

**位置**

- `internal/service/checkout.go:226-257`：`VoidReceipt` 只做 `UPDATE receivables SET voided=1`，註解自承「不回沖已完成的結帳或庫存/帳務」。
- `internal/handler/workorders.go:752`：卻告訴使用者「如需更正請另行開立沖銷單」。
- 全 repo 沒有沖銷單/貸項通知（credit note）功能。

**影響（已 paid 的工單）**

- 工單仍是 `paid`，庫存仍已扣，`customers.total_spent` 沒減。
- 收款報表/應收帳款因為 `voided=1` 而少一筆 → 帳面營收下降，但工單與庫存沒動。
- 作廢是 owner 限定的「更正」操作，結果越更正越對不上。

**建議（二選一）**

1. 禁止作廢已觸發結帳的收款，要求先做退貨/退費流程；或
2. 作廢時在同一交易內反轉：工單退回 `completed`、回補庫存、扣回 `total_spent`、留下反轉異動紀錄。

同時把 `workorders.go:752` 的文案改成實際存在的操作，避免承諾不存在的功能。

### P0-4. LINE 手機自動綁定可被用來冒用客戶帳號（含門號列舉）

**位置**

- `internal/handler/line_webhook.go:273-325`：任何未綁定的 LINE 使用者，只要送出一個「唯一對應某客戶」的手機號碼，就立即綁定，**沒有 OTP、沒有櫃檯確認**。
- `internal/handler/line_webhook.go:216-226`：同一客戶只能被一個 LINE 帳號綁定；攻擊者先綁成功後，真正車主會被拒絕（「此客戶已綁定其他 LINE 帳號」）。
- 回覆內容會區分「查無此號碼」／「對應 N 筆」／「已為您連結」，等於提供門號列舉 oracle；也沒有 rate limit。

**影響**

- 知道客戶手機號碼的人（員工、前員工、送貨廠商、外流名單）可以先綁定該客戶。
- 綁定後可查維修進度、車輛履歷、估價，並可代替客戶按下維修授權（核准追加維修）。
- 真正的車主反而被鎖在外面，需要人工解綁。

**建議**

- 改成「送出門號 → 產生一次性驗證碼（簡訊或櫃檯提供）→ 輸入後才綁定」。
- 或最保守：LINE 只送出綁定申請，由櫃檯在客戶頁按「確認綁定」。
- 不論哪種，回覆一律統一（避免「查無此號碼」 vs「已綁定」的差異），並加 per-user/per-IP 限流。

> 補充：`/api/passbook` 用 `line` 查詢參數當身分（`internal/handler/passbook.go:36-40`）本身已要求該 LINE ID 必須綁定該客戶，且有枚舉防護；但 raw LINE user ID 放在 URL 會進 access log／瀏覽器歷史。這是 ROADMAP 已接受的設計取捨，建議至少改成短效簽章 token，或確認 reverse proxy 不記錄 query string。

### P0-5. 收款金額沒有對帳：可超收、明細與工單不一致

**位置**

- `internal/service/checkout.go:81-84`、`157-170`：只檢查各金額不為負，沒有檢查 `pay_total == cash + card + check + transfer`。
- `internal/handler/receivables.go:403-411`：`pay_total` 只在為 0 時自動加總；同時填了不一致的數字也照收。
- `detail_total`／`real_total`／`discount`／`tax` 由表單自由填（`web/pages/stage7_forms.templ:360-364`），沒有和工單 `total_amount` 對帳，server 也沒擋負的 `discount`/`tax`。
- 沒有「累計收款不得超過工單總額」的檢查；對已 `paid` 的工單仍可再新增收款（`checkoutTx` 會因 `status='paid'` 直接回 nil，但收款列已寫入）。

**影響**

- 收款單加總與付款方式對不上，帳務/對帳困難。
- 可誤收或重複收，系統不會提示。
- 收據上的「明細合計/折扣/稅額」可與工單金額無關，客訴時無法佐證。

**建議**

- service 層驗證：`pay_total == cash+card+check+transfer`（允許 1 元以下誤差或全整數）、`pay_total > 0`、`discount/tax >= 0`。
- 關聯工單時驗證 `detail_total` 與工單明細一致（或直接由工單帶入、不可修改）。
- 新增收款前檢查「累計已收 + 本次 <= 工單總額」，並擋已結帳工單的重複收款（除非走退款/補收流程）。

### P0-6. 收款單號用 `COUNT(*)` 產生，且 DB 沒有 UNIQUE

**位置**

- `internal/handler/receivables.go:569-578`：`SELECT COUNT(1) ... LIKE 'RCV-YYYYMMDD-%'` 後 +1。
- `internal/db/migration/013_receivables.up.sql:79`：只有一般 index，不是 UNIQUE。
- `internal/service/checkout.go:90-96`：同號但內容不同時不會被冪等邏輯擋下。

**影響**：兩位櫃檯同時收款（或多分店/多視窗）可能拿到同一個 `RCV-...-001`；帳務匯出、對帳、搜尋都會混淆。

**建議**

- `voucher_no` 加 UNIQUE（若舊資料有重複，先清理或加部分唯一索引）。
- 取號改用「當日序號表 + 交易」或 `INSERT ... ON CONFLICT` 重試，不要用 COUNT。
- 取號與寫入放在同一交易。

### P0-7. `customers.unpaid_amount` 永遠是 0，顧客列表的「未付」不可信

**位置**

- `internal/service/checkout.go:428-432`：結帳時把 `unpaid_amount` 直接設為 0。
- 全 repo 沒有任何地方**累加**這個欄位（只有讀取與歸零），所以新資料的「未付」永遠是 0。
- 顯示位置：`internal/handler/customers.go:35,99`、`web/pages/customer.templ:82-83,120-121`。

**已重現**：客戶有一張 `completed` 但未付款的工單（`unpaid_amount=80`），再結帳另一張工單 → `unpaid_amount` 變成 0。

**影響**

- 顧客列表的「未付」會讓櫃檯以為沒有欠款；真正的未收款只有「應收帳款」報表（`internal/handler/print_docs.go:415-422`，用 receivables 即時計算）才正確。
- `internal/service/checkout_test.go:99-100` 反而把「結帳後 unpaid=0」寫成預期行為，之後改程式會卡測試。

**建議**

- 最乾淨：移除 `unpaid_amount` 欄位，列表改用 `receivables` 子查詢即時算（和 AR 報表同一公式）。
- 若保留：結帳時只加「本次實收」，並在工單進入 `completed` 且未付清時累加；同步修正測試。

## 2. P1 — 高優先（權限與資料正確性）

### P1-1. 技師可讀任意工單的收款單／完工證明（IDOR）

- 路由：`main.go:312`（收款單）、`main.go:317`（完工證明）都是 `AllStaff`。
- `internal/handler/receipt.go:17` 的 `PrintWorkOrderReceipt` **沒有** `canViewWorkOrder`、也沒有 `canSeeMoney`；只要換 ID 就能看任何客戶的工單金額、客戶姓名、電話、車牌。
- `internal/handler/print_docs.go:168` 的 `PrintWorkOrderCompletion` 同樣沒有工單權限檢查。
- 對照：`ShowWorkOrder` 有 `canViewWorkOrder`（`internal/handler/workorders.go:674-689`），技師只能看被分配的工單。

**建議**：兩個列印 handler 都先呼叫 `canViewWorkOrder`；收款單再加 `canSeeMoney`（或明確決策「技師可看自己工單的報價」但不可看付款明細）。

### P1-2. 技師可讀任意工單的工時紀錄

- `internal/handler/worklogs.go:74` 的 `ListTechnicianWorklogs` 只查 `work_order_id`，沒有 `canViewWorkOrder`。
- 路由 `main.go:304` 是 `AllStaff`。
- 工時/備註可能包含人員表現與施工細節；技師只要換工單 ID 就能讀。

**建議**：加 `canViewWorkOrder(user, woID)`；或限制技師只能看自己參與的工單。

### P1-3. 「技師不看財務數字」的政策沒有落實到所有頁面

`canSeeMoney` 只涵蓋庫存成本、收款、報表、分析、佣金（`internal/handler/authz.go:123-127`），但以下地方對技師直接顯示金額：

- 客戶列表：「累計消費」「未付」（`internal/handler/customers.go:35,99`、`web/pages/customer.templ:69,82-83,120-121`）。
- 工單列表：`web/pages/workorder_list.templ:132` 無條件顯示 `TotalAmount`。
- 工單詳情：`web/pages/workorder.templ:110-113` 顯示明細合計與工單總額。
- 收款單：見 P1-1。

**影響**：與 `canSeeMoney` 的註解「技師不看營收」矛盾；即使這是刻意（技師需要知道報價），也應該明確定義哪些金額可看，並在文件寫清楚。客戶的「累計消費/未付」屬於財務資料，建議至少隱藏。

### P1-4. 員工個資對所有登入者開放（含身分證號）

- `main.go:231`：`GET /staff` 是 `AllStaff`。
- `internal/handler/staff.go:61,74`：查詢與回傳 `national_id`、生日、加退保日；`main.go:113` 的 `/api/staff/search` 只要登入就能用，還可以用身分證號搜尋。
- `web/pages/staff.templ:99-100,138`：直接顯示身分證號。

**影響**：個資法風險；技師/櫃檯可以看到全店員工（含眷屬）的身分證與保險資料。`docs/USER_GUIDE_zh-TW.md:195` 已提醒，但「提醒」不能取代權限。

**建議**：`/staff` 與搜尋 API 改 `OwnerOnly`（或 owner+counter 且隱藏身分證，僅 owner 可看完整號碼）；列表只顯示末四碼。

### P1-5. 工單狀態可任意跳轉（pending → paid、completed → pending）

- `internal/handler/workorders.go:735-786`：只擋「已 paid 不能再改」，其餘任何合法狀態都能互跳；若沒有必填 SOP／未決授權，`pending` 可直接進 `paid` 觸發結帳。
- 沒有狀態機/允許轉換表，也沒有「跳過完工」的警告。

**影響**：誤按就可能把未施工的工單結帳（搭配 P0-1/P0-2），或把已完成工單退回進行中造成流程混亂。

**建議**：明確定義允許的轉換（pending → in_progress → waiting_parts/… → completed → paid），後端拒絕非法跳轉；`pending` 直接 `paid` 應要求 owner 覆核或明確的「快速結帳」權限。

### P1-6. 進貨不會更新既有零件的成本價

- `internal/handler/purchase_orders.go:488-505`：收貨只 `UPDATE inventory_items SET stock_quantity = stock_quantity + ?`，沒有更新 `cost_price`。
- 只有「自動新建零件」時才帶入成本（`purchase_orders.go:553-558`）。

**影響**：零件漲價/降價後，庫存成本與毛利分析（analytics）仍用舊成本，越賣越不準。

**建議**：收貨時依 `unit_cost` 更新成本（可選加權平均或最後進價），並記錄成本異動；或在收貨畫面提供「是否更新成本價」選項。

### P1-7. `DB_PATH` 相對路徑被靜默忽略；`busy_timeout` 只套用一條連線

- `internal/db/db.go:105-118`：只有 `file:` 或絕對路徑會被採用；其他（包含非空的相對路徑，例如 `DB_PATH=data/shop2.db`）會**默默**連到 `./data/autorepair.db`。註解自己說曾因此讓隔離測試打到正式庫。
- `internal/db/db.go:156`：`PRAGMA busy_timeout=5000` 只對連線池中的一條連線生效；`SetMaxOpenConns(8)`（`db.go:134`）。
- DSN 的 `_busy_timeout=5000` 與 `_journal_mode=WAL` 是 mattn/go-sqlite3 語法，modernc.org/sqlite 只認 `_pragma=busy_timeout(...)`（`db.go:144-145` 已承認 journal_mode 無效）。`docker-compose.yml:42` 也用了無效參數。

**影響**：多工寫入時，其餘 7 條連線的 busy timeout 為 0，可能立刻回 `database is locked`；相對路徑設定會讓人以為換了 DB，其實沒有。

**建議**：相對路徑改成 `filepath.Join(dataDir, cfg.DBPath)` 或明確報錯；`busy_timeout` 改用 `_pragma=busy_timeout(5000)` 放進 DSN，確保每條連線都套用。

### P1-8. 登入沒有速率限制／鎖定；預設密碼只檢查非空

- `internal/handler/auth.go:71-129`：沒有嘗試次數、延遲或鎖定；只有 bcrypt 的成本。
- `internal/seed/seed.go:36-44`：只檢查 `password == ""`，沒有長度/複雜度；且 seed 是冪等的，事後改 `RUN_SEED` 不會修正已建立的弱密碼。
- `test_login.py:38-39` 直接寫死 `owner` / `owner1234!`。

**建議**：登入失敗加延遲與帳號/IP 限流（例如 5 次後鎖 15 分鐘）；首次登入強制改密碼；密碼至少 12 字元；測試腳本改讀環境變數並移出可提交路徑。

### 4-2. 測試覆蓋與建議補的案例

目前覆蓋率偏低（handler 21.4%、session 7.8%、db 14.9%），而且現有測試把部分錯誤行為寫死（`internal/service/checkout_test.go:99-100` 斷言結帳後 `unpaid=0`）。

優先補這些（都會直接抓到上面的 bug）：

1. **收款不應提前結帳**：pending/in_progress 工單 + 全額收款 → 狀態不得變 `paid`、庫存不得扣。
2. **0 元工單**：`total=0` + 任意收款 → 不得自動結帳。
3. **超收/金額不一致**：`pay_total != cash+card+...`、`pay_total > 工單總額`、負折扣 → 應拒絕。
4. **作廢回沖**：paid 工單的收款作廢 → 工單狀態、庫存、`total_spent` 的行為要明確定義並測試。
5. **未付金額**：同一客戶兩張工單（一張未付、一張結帳）→ `unpaid_amount` 不得被清零；顧客列表的「未付」要正確。
6. **授權矩陣**（table-driven）：對 owner/counter/technician × 敏感路由（收款單、完工證明、工時、員工、客戶金額）斷言 200/403。
7. **狀態機**：非法轉換（pending→paid、completed→pending）應拒絕。
8. **併發取號**：兩個 goroutine 同時建收款 → `voucher_no` 不得重複。
9. **進貨成本**：既有零件收貨後 `cost_price` 應更新（若決定要更新）。
10. **DB 設定**：相對 `DB_PATH` 要嘛正確使用、要嘛明確報錯；`busy_timeout` 要在每條連線生效。

另外建議加一個最小的 **HTTP 煙霧測試**：登入 → 開工單 → 加項目 → 收款 → 列印，確認 CSRF/redirect/權限沒有回歸。

## 6. 做得好的地方（不是只有缺點）

- 結帳、庫存扣減、客戶累計在同一交易（`checkout.go`），且有 rollback/冪等測試。
- CSRF 是「session 綁定 + header/表單雙送 + constant-time 比較」，不是隨便的 double-submit（`internal/handler/csrf.go`）。
- 照片改為「工單 ID + 序號」並檢查 `canViewWorkOrder`（FIX_PLAN S1 已修）。
- 大量使用 Templ，動態 HTML 有 escape；`templ.Raw` 的已知風險有盤點文件。
- 軟刪除/`active_*` view、migration 編號、備份腳本、Docker/compose、使用手冊與 SRS 都有，維護性以個人專案來說很好。
- 成本價在庫存/分析頁有依角色隱藏；收款/報表路由有 `CounterUp` 粗篩。
- LINE webhook 有簽章驗證與 1MB body 限制；passbook 有列舉防護設計。

## 7. 尚待你決定的產品問題

這幾個不是 bug，但會影響修法：

1. **技師到底能不能看工單金額/報價？** 目前程式多數地方看得到，但 `canSeeMoney` 的註解說不行。先定政策，才能決定 P1-1/P1-3 要藏到什麼程度。
2. **收款頁是否要支援「訂金/預收」？** 若不要，最簡單就是只允許 completed 工單；若要，必須把「預收」與「結帳」分開。
3. **作廢已結帳收款要「禁止」還是「自動回沖」？** 自動回沖技術上可行，但需要明確的退費/折讓規則。
4. **是否需要統一發票/電子發票？** 目前只有收據與稅額欄位，沒有發票號碼/字軌；若店內需要，這是另一個模組。
